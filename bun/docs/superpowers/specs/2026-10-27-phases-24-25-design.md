# Design: Phases 24 and 25

Date: 2026-10-27
Status: approved by the user (full authority given); both phases are
implemented (2026-10-28)

## Phase 24: struct patterns in `match` ("class patterns")

The `match` statement walks the shape of a value: a literal, a binding, a
wildcard, a type, a range, a list, a dict or an enum variant. A struct
value is the one shape that cannot be matched on its own: the program has
to write the fields as a dict pattern by hand, and nothing checks that the
value is a value of the struct at all.

Rust matches a struct and an enum variant with a pattern that names the
type and binds its fields. Python matches a class the same way since
PEP 634. Bun takes the shape of both: a pattern names the struct and
binds its fields.

### Syntax

```
match p {
    Point(x: 0, y) => print("origin")
    Point(x, y) => print(x + y)
}
```

- `Point(x: 0, y)` — the value has to be a `Point`; `x` has to equal
  `0`, and `y` is bound.
- A bare name in the field list binds that field: the sub-pattern of a
  field may be any pattern, so a field may be a literal, a nested struct
  pattern, an `or` or a binding.
- A pattern of a struct with no fields, `Point()`, matches a value of the
  type with nothing bound.

### Semantics

- The value has to be a struct of the named type: a struct of another
  type, a dict, a list or a number does not match. The type of the
  subject is checked when the checker knows it, and the runtime checks
  it otherwise.
- The struct value holds its fields, so a field pattern tests the field
  the way the pattern of a dict entry tests it.
- The plan is one more kind of plan, the way the plan of an enum variant
  is the plan of a dict: `["struct", name, [[field, plan], ...]]`.
  Every engine tests a value with the same code.

### What is checked before the program runs

- The struct name has to name a struct.
- A field of the pattern has to name a field of the struct, the way the
  checker counts the fields of a constructor call.
- The subject of the match may not be refused on a mistyped pattern: the
  type of the subject is left to the runtime when it is not known.

### Engines

- The plan lives in `patterns`, so the tree, both VMs and the self-hosted
  front end match the same way.
- The C backend compiles the match of the language: the struct pattern
  becomes the test of the type and the tests of its fields, the way the
  dict pattern does.

## Phase 25: `with` and `scope` under the C backend

The C backend translates the register code of a program into C. The
`with` statement and the `scope` statement are refused by name today.
Phase 25 makes both work under the backend, so every engine of the
language runs the same program.

### Semantics that carries over

- `with` on a context manager is a dict with `__enter__` and `__exit__`:
  the body runs between the two calls, and the answer of `__exit__`
  decides whether a failure goes on.
- `scope` runs its body in a task group: the tasks it spawned are joined
  before the scope ends, and a failure cancels the group.

### Approach

1. Make the register code of both statements carry what the backend
   needs, the way the match was taught to the backend before: the
   backend either compiles the shape or refuses it by name.
2. Keep the two VMs as the reference, and prove the parity on the golden
   corpus and a case for each statement under every engine.

### What the implementation does

- The `with` statement already ran under the backend: the `__enter__` and
  the `__exit__` of a target are a call of a method of a dict.
- The `scope` statement opens a group of tasks and closes it when the
  body ends. The backend writes `bun_scope_enter` and `bun_scope_exit`,
  and the runtime of the backend holds the group.
- A task of the C backend runs on a thread of its own, the way a task of
  the machines runs on a thread of its own. The values of the program
  live in an arena of the thread that made them, and the arena of a task
  moves to the list of the ended tasks when the task ends, so the value a
  task made is still there for the task that joins it.
- The error of a task is an error of the task: the place of the failure
  and the message of it are kept, and the task that joins the task sees
  the failure instead of an answer.
- The backend refuses nothing of the two statements any more.

## Not in scope

- The WASM backend, the counted fusion, the optimising JIT.
- The `?` on a value of a type that is not known yet at the checker.
- A second edition of the protocols: the structural check stays.
