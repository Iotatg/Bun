# Phase 13 — The C Backend

Date: 2026-10-20
Research: `docs/superpowers/research/2026-10-20-bun-c-backend.md`
Status: done

## The goal

A program of Bun that runs at the speed of the machine it is on. The
backend reads the register code of Phase 11, emits C, and lets the system
compiler finish the job.

The acceptance criteria are the ones of the research document:

1. The same bytes — the golden corpus prints the same under the backend.
2. The same errors — a program that fails fails with the same message.
3. A clear refusal — a construct the backend cannot translate is refused
   at compile time, by name.
4. A number — the speed of the backend against the stack VM is measured
   by a tool and published.

## The rules

- The backend never changes the language. The stack VM stays the
  reference and the default engine; the backend is opt-in with
  `--engine c`.
- The backend says no rather than guessing. A construct it cannot
  translate is refused at compile time with the name of the construct.
- The oracle is the golden corpus. Every program of the corpus that the
  backend supports prints the same bytes under every engine.
- The numbers are published. A benchmark that measures the backend
  against the stack VM, printed by a tool, not an adjective in a
  document.

## The notes of the phase

- The register file of a function is a heap array when the function can
  raise an error, because the automatic storage of C is indeterminate
  after a `longjmp`. The functions without a `try` keep the array on
  the stack.
- The size of the register file is the highest slot the code touches,
  plus one. The instructions that write more than one slot (`DUP`,
  `BUILD_LIST`, `BUILD_DICT`, `SLICE`, `STORE_SLICE`, `UNPACK_PLAN`,
  `CALL`, `METHOD_CALL`) are counted, because an off-by-one here is a
  buffer overflow that shows itself only with the optimisation of the
  compiler.
- The assertion of Bun is a jump: the code that skips the assertion is
  already in the register code, so the instruction that reaches the
  assertion always fails. The backend must not test the condition
  again.
- The message of a thrown error is the value that was thrown. The cause
  of the error is only shown in the picture of the failure, and the
  backend has no picture, so the cause is dropped.
- The refusal of a builtin happens before the code is emitted: a program
  that calls `secret` is refused at compile time, with the name of the
  builtin, instead of failing at run time with an undefined variable.
- The list of the builtins of the backend is checked against the list
  of the runtime by the test suite, so the two cannot drift apart.
