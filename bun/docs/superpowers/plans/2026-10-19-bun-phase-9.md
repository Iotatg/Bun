# Bun Phase 9 — The Native Stacks — Implementation Plan

Date: 2026-10-19
Design: `docs/superpowers/specs/2026-10-19-bun-advanced-language-design.md` §5
Research: `docs/superpowers/research/2026-10-19-bun-language-research.md` §5.3

---

## Objective

Give Bun the four domain stacks that make the language useful on its own:
a numerical core for AI work, a security layer, a game engine core and a
web stack. Every stack is written **in Bun**, uses the Phase 6/7 language,
and is replaceable by the user.

The rule that makes this possible: a stack is a *library*, not a language
feature. Bun stays small; the stacks are ordinary Bun modules that the
runtime knows how to find.

The API of a stack is a set of **module functions**, not methods: Bun has
no classes, so `get(router, "/", handler)` is the way a route is added and
not `router.get("/", handler)`. The examples below follow the code.

## 1. `bun:` module resolution

A native stack is imported by name:

```bun
import { tensor, matmul } from "bun:tensor"
```

The path is not a file path and not a package name, so the module resolver
gains one case: a path that starts with `bun:` names a module of the
language itself. The resolver maps it to `<library>/bun/<name>.bun`, where
`<name>` is the part after the colon. A stack that does not exist is a
normal "cannot find module" error, not a crash.

The rule is deliberately narrow. `bun:` is the only prefix that the
resolver claims, and it can only name a file inside the language's own
library directory. A user module can never be loaded through it, so the
prefix cannot be used to smuggle a file past the module rules.

## 2. `bun:tensor` — the numerical core

```bun
import { tensor, zeros, ones, matmul, softmax, relu, adam, sum } from "bun:tensor"

let x = tensor([[1.0, 2.0], [3.0, 4.0]])
let w = tensor([[0.5, -0.2], [0.1, 0.9]])
let y = matmul(x, w)
let p = softmax(y, 0)
```

### Representation

A tensor is a dictionary with two keys:

| Key | Meaning |
|-----|---------|
| `data` | the flat list of numbers, row-major |
| `shape` | the list of dimensions |

There are no classes in Bun, so a tensor is a plain dictionary with a
marker key `kind` whose value is `"tensor"`. The operations check the
marker and raise a clear error for anything else. This is duck typing
with a name, which is the Bun way to say "this is a tensor".

Flat storage in row-major order is the layout every BLAS-compatible
library assumes, and it is the layout the operations want: `matmul` walks
three flat loops and never builds a temporary matrix.

### The operations

| Operation | Shape rule |
|-----------|------------|
| `tensor(data)` | infers the shape from nested lists |
| `zeros(shape)`, `ones(shape)`, `full(shape, value)` | any rank |
| `matmul(a, b)` | `[m,k] x [k,n] -> [m,n]` |
| `add`, `sub`, `mul`, `div` | elementwise, same shape, or a rank-1 vector against a rank-2 matrix |
| `transpose(a)` | rank 2 only |
| `reshape(a, shape)` | the same number of elements |
| `softmax(a, axis)` | a numerically stable softmax along one axis |
| `relu(a)`, `sigmoid(a)`, `tanh(a)` | elementwise |
| `sum(a)`, `mean(a)`, `max(a)`, `min(a)` | over the whole tensor |
| `adam(params, grads, state, lr, beta1, beta2, eps, step)` | the Adam update |
| `backward(loss)` | the reverse-mode gradient of a tape |

### Determinism

The reductions use a **fixed pairwise order**: the elements are summed in
a tree, and the tree is fixed by the length of the tensor. The same
tensor therefore gives the same sum on every run, on every machine. This
is a hard requirement, not a nicety: a training run is only comparable
with another training run if the arithmetic is reproducible.

The naive left-to-right sum is *not* used, because its result depends on
the order of the additions and the rounding of each step.

### Autodiff

`backward` walks a tape in reverse. Every operation that touches the data
records how to push a gradient back, and the tape is walked from the last
operation to the first. The gradient of a scalar loss with respect to
every leaf is returned in a dictionary keyed by the name of the variable.

The implementation is the classic reverse-mode tape: it is simple, it
works for any composition of the operations above, and it needs no
operator overloading, which Bun does not have.

## 3. `bun:sec` — the security layer

```bun
import { secret, capability, redact, sandbox } from "bun:sec"

let token = secret(read_env("OPENAI_API_KEY"))
let policy = capability({ "net": ["api.openai.com"], "fs": ["./data"] })
let result = sandbox(policy, fn () { call_api(token) })
```

- `secret(value)` returns a `Secret`, the redacted type of §2.7. The
  value is never in `str()`, `dump()` or an error message.
- `capability(manifest)` builds the manifest of what a piece of code may
  do: the hosts it may reach, the paths it may read, whether it may
  spawn a process, whether it may read the clock.
- `sandbox(policy, fn)` runs the closure under the manifest. The runtime
  asks the policy before every network call, file access and process
  spawn that the closure makes, and a violation raises a runtime error
  that names the blocked capability.
- `redact(text)` removes the values that are marked secret and the
  patterns that look like secrets: `sk-...` keys, AWS access key ids,
  bearer tokens, private key blocks.

The runtime hook is the interesting part. The sandbox is not a promise in
the documentation; it is a check in `bun/builtins.py` before the socket
is opened and before the file is read.

## 4. `bun:game` — the game engine core

```bun
import { vec2, vec2_add, vec2_scale, rect, circle, Game, on_update, advance } from "bun:game"

let game = Game({ "width": 800.0, "height": 600.0 })
on_update(game, fn (dt) {
    player["pos"] = vec2_add(player["pos"], vec2_scale(player["vel"], dt))
})
advance(game, 1.0 / 60.0)
```

- **Math:** `vec2`, `vec3`, `vec4`, `quat`, and the operations on them.
  A vector is a list, so the arithmetic is a plain loop.
- **Shapes:** `rect`, `circle`, `point`, `segment`, `ray`; the
  intersection tests and the containment tests.
- **The loop:** a fixed timestep of 1/60 s with an accumulator. The
  simulation always advances in steps of the same size, so a physics
  replay is the same every time. The frame time is an input to the
  accumulator, never the size of a step.
- **Entities:** struct-of-arrays storage with a free list. An entity is
  an index, and the data of the entities lives in flat lists, so the
  update is a tight loop over a flat list.
- **Broadphase:** a uniform grid, so the collision test does not compare
  every pair.

## 5. `bun:web` — the web stack

```bun
import { Router, get, serve, serve_forever, html, raw } from "bun:web"

let app = Router()
get(app, "/", fn (req) { return html("<h1>hello</h1>") })
get(app, "/users/:id", fn (req) { return html("<p>" + req["params"]["id"] + "</p>") })
let server = serve(app, 3000, "0.0.0.0")
serve_forever(server)
```

- `Router` — path parameters only (`/users/:id`) and a tail (`*rest`).
  No regular expressions: a route is a list of literal segments and named
  parameters, and the match is a walk over the segments.
- `html` — auto-escaping by default. The value of a template is escaped,
  and a fragment that is already markup is marked with `raw(...)`. XSS by
  default is the failure that the industry keeps having.
- `serve` — an HTTP/1.1 server. The runtime gained a listening socket:
  `tcp_listen`, `tcp_accept` and `tcp_close`. Every connection is served
  in its own task. The response closes the connection, so keep-alive and
  chunked responses are still to do.
- `websocket` — RFC 6455: the handshake, the framing, the masking of the
  client frames and the close handshake. The mask is taken out bit by bit,
  because the language has no bit operators yet.
- `proxy` — a reverse proxy to a backend service, the pattern the
  project's own rules require for a frontend and a backend behind one
  port.

## 6. Tests

Every stack is tested twice: once through the Python pipeline and once
through the self-hosted front end, because the two must agree. The test
file is `tests/test_stacks.py`; it holds 75 tests and every one of them
runs on both engines.

The tensor tests are the strict ones: every operation has a value that
was computed by hand or by an independent implementation, and the
autodiff gradients are checked against a finite difference.

## 7. What is deferred

- **The GPU backend** of the game stack. The bitmap and SDF font
  renderers come first; a GPU backend is a documented future path.
- **The `bun dev` watcher.** The reverse proxy comes first.
- **The tensor types beyond `float64` and `int64`.** The dtype is part of
  the representation but only one interpretation is used.
- **The FFI profiles.** The allowlist stays a source file.
- **The bit operators of the language.** The websocket mask is taken out
  bit by bit in `bun:web`; the operators belong to the language itself
  and are a language change, not a stack change.

## 8. What came after

Two items that the plan had deferred arrived later:

- **Keep-alive and chunked responses** in `bun:web`. The server now speaks
  HTTP/1.1 with a connection that stays open, serves two requests that
  arrive in one write, and writes a streamed answer with the chunked
  encoding. `chunked(pieces)` builds such an answer, `to_hex(value)` and
  `index_of_bytes(haystack, needle)` are the helpers of the byte level,
  and `header_value(headers, name)` reads a header whatever the case of
  its name is.
- **The bit operators of the language.** They came with Phase 10, and the
  websocket mask uses them now.
