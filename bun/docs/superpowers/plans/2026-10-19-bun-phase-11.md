# Bun Phase 11 — The Native Tier — Implementation Plan

Date: 2026-10-20
Design: `docs/superpowers/specs/2026-10-19-bun-advanced-language-design.md` §7
Research: `docs/superpowers/research/2026-10-19-bun-language-research.md` §5

---

## Objective

Phase 11 is the "C++-like speed" deliverable. The language is already fast
for a dynamic language, because the work of Phase 3 took the method dispatch
out of the hot path and gave the compiler an inline cache. What is still
missing is the shape of the machine: every value goes through a stack, and a
stack machine pays for every value with a push and a pop.

The register VM replaces the stack with a register file. The program becomes
a sequence of three-address instructions:

```
ADD r3, r4, r5
```

instead of a sequence of pushes and pops that the interpreter has to undo
one by one. The bytecode stays safe: a verifier runs before the code runs,
and it proves the shape of the program (the registers, the jumps, the stack
depth at every merge point) the way the JVM proves the shape of a class
file.

The plan is not to throw the stack VM away. The stack VM is the reference
semantics, and the register VM is a *tier* on top of it:

```
source ──> stack bytecode ──> registerizer ──> register code ──> register VM
                │                                        │
                └──────── the golden corpus ───────────┘
```

Every program must print the same thing under every tier, and the golden
corpus of the parity suite is what proves it.

## 1. The register code format

A program of the register tier is a list of instructions. Every
instruction is four cells: the opcode and three operands. The cells hold
integers, and the meaning of an integer depends on the opcode, as it does
in every real machine:

```python
("MOV", dst, src, 0)          # a register moves to another register
("CONST", dst, const_index, 0) # a constant moves to a register
("ADD", dst, a, b)            # the sum of two registers
("CALL", dst, arg_base, argc)
("JUMP", target, 0, 0)
("JUMP_IF_FALSE", a, target, 0)
```

The register file is a list of slots in the frame. The format is a plain
list of tuples, so the code of a program can be printed, compared and
written to a file without a serializer.

**The values stay dynamic.** Bun is a dynamic language, and a dynamic
language does not get faster by pretending it is not. What the typed part
buys is the verifier: the instruction knows what kind of thing its
operands are (a register, a constant, a jump target), so the verifier can
prove that the program is well formed before it runs.

## 2. The registerizer

The registerizer is a pass over the stack bytecode that simulates the
stack and turns it into registers. It is the standard lowering:

- the virtual stack is a list of register numbers;
- `LOAD_CONST` becomes `CONST r, k`;
- `LOAD_NAME` becomes a load that reads the environment into a register;
- `BINARY` pops two registers and pushes the result into the first one;
- a call pushes the arguments into consecutive registers and writes the
  result into the first one.

**The spilling.** The register file is finite (32 slots to start). When
the virtual stack grows past the number of registers, the oldest register is
spilled to the frame's spill area and a new one is used. A program with a
deep expression tree spills, and a program with a loop body does not.

**The jump targets** are rewritten: the stack bytecode counts
instructions, the register code counts register instructions, and the
registerizer keeps a map from one to the other.

**The exception handling** is the hard part of the lowering, because a
`try` block must be able to restore the stack to the depth it had when
the block started. The registerizer keeps the depth at every handler and
emits the code that truncates the register stack to it.

## 3. The register VM

The register VM is an interpreter over the register code. It has the same
environments, the same builtins, the same errors and the same messages as
the stack VM — it is the same language, run by a different machine.

The inner loop is a dispatch over the opcode with the operands read once:

```python
opcode = code[ip]
ip += 1
if opcode == OP_MOV:
    registers[code[ip]] = registers[code[ip + 1]]
    ip += 2
```

The inline caches of Phase 3 carry over: the method dispatch cache is
keyed by the same `(type, method)` pair ✓.

## 4. The verifier

The verifier runs on the register code before it runs, and it proves:

- every register index is inside the frame;
- every jump target is an instruction of the same function;
- the stack depth at the target of every backward jump is the depth at the
  jump itself, so a loop cannot grow the stack;
- every function ends with a return or a halt.

A program that does not pass the verifier is a runtime error with a
message that says which function and which instruction are wrong. The
verifier is a safety net, and the registerizer is written so that it never
fails on a program the stack VM accepts — the test that says so is the
golden corpus.

## 5. The superinstruction tier

The superinstruction tier is the cheap half of a JIT.  Two instructions
that always run one after the other are replaced by one fused instruction
that does the work of both:

```
LOAD_NAME r0, "count"      CONST r1, 1
        ->  LOAD_NAME_CONST r0, <the pair in the pool>
```

The fusion is done at load time, on the code that is already verified, so
the fused instruction is as safe as the two it replaces.  The fused code
goes through the verifier a second time, because the fusion changes the
shape of the program.

The fusion is careful about two things:

- the second instruction of a pair must not be the target of a jump, or a
  jump that wanted to run only the second instruction would run the first
  one as well;
- the two instructions must sit at the depth the fusion expects, so the
  depth of the expression stays the same on every path.

The pairs that are fused are the ones that carry no side effect: the
loads of a name and the loads of a constant.  The plan of the work of a
fused instruction lives in the constant pool, and it keeps the place of
the second part, so an error that happens there is reported at the right
place.

The flag `--tier` turns the tier on:

```bash
bun --engine register --tier file.bun
```

The tier is off by default, the way the profiler of `bun compile
--profile` is off by default.  A program that runs under the tier has to
print exactly what it prints without it, and the golden corpus is what
proves it.

### What came after

The plan described the tier as *counted*: the interpreter counts how often
each pair of instructions runs next to each other, and past a threshold
the pair is replaced by a fused instruction.  What was built is the
static half of that idea: the fusion happens at load time, on the pairs
that the code holds, and the count of the pairs is what
`bun.regfuse.count_pairs` reports.  The counted half — a fusion that
depends on what the program did while it ran — belongs to a real
optimising JIT, and it is listed under "What is deferred" below.

## 6. The engine switch

```bash
bun --engine tree file.bun                   # the tree
bun --engine vm file.bun                     # the reference
bun --engine register file.bun               # the register tier
bun --engine register --tier file.bun         # with the superinstructions
```

The default stays the stack VM, because the stack VM is the reference
semantics and the fastest of the three on a small program: the lowering
costs time and the win comes from the loop.

| `tests/golden/tiers.bun` | a program that uses the whole language, run under every engine |

| `tests/test_stacks.py` | the native stacks under the tree, the VM, the register VM and the tier |

The rule of the phase: a program that prints something different under
another engine is a bug in the tier, never a difference in the language.

## 8. What is deferred

- **The AOT backends.** The C backend and the WASM backend of the spec
  §7.3 come after the register tier is stable, because they need the
  register code to be final.
- **A full JIT.** The superinstruction tier is the safe half: the fusion
  is static and happens at load time.  A fusion that depends on what the
  program did while it ran — the counted half of the plan — is a project
  of its own, and so is a real optimising JIT.
- **The typed register file.** The language is dynamic, so the values in
  the registers stay dynamic; only the instruction shapes are checked.
