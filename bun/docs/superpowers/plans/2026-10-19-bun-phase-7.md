# Bun Phase 7 — Performance and Structured Concurrency — Implementation Plan

Date: 2026-10-19
Design: `docs/superpowers/specs/2026-10-19-bun-advanced-language-design.md` §3

---

## Objective

Make Bun *fast* on the workloads it is built for, and give it the one
concurrency construct that removes the largest class of concurrency bugs:
a scope that owns the tasks it spawns.

Phase 6 completed the surface language. Phase 7 tunes the runtime against
that finished surface, so the measurements are taken against real code
rather than a moving target.

## 1. Startup budget

The startup of the language is a published number, not a hope.

| Metric | Budget |
|--------|--------|
| `bun` hello program, tree engine | 120 ms |
| `bun` hello program, VM engine | 140 ms |
| import of the language | 120 ms |

`tools/bench.py` measures the fastest of seven warm runs and fails when a
budget is missed. `tests/test_startup.py` runs the same measurement inside
the test suite, so a regression is caught by `pytest` and not by a user.

## 2. Lean startup

The import of the language used to cost about 165 ms. Three changes brought
it to about 35 ms:

- `bun/records.py` replaces `dataclasses` for the AST, the tokens and the
  runtime values. A dataclass costs about a millisecond to create; the
  language creates 35 of them on every start.
- `TokenType` became a set of plain string constants. An `enum` costs a
  fifth of the startup time, and only the name of a token type is ever
  used.
- `typing` is gone from the hot path. `from __future__ import annotations`
  keeps the annotations readable without importing the module.

## 3. Method dispatch cache

`ops.method_call` used to walk four `isinstance` checks and a table lookup
for every method call. The method tables are static, so the result of the
lookup only depends on the concrete type of the receiver and the name of
the method: the result is cached under that key.

The tree engine, which spends a larger share of its time in the method
path, got about a third faster on a method-heavy benchmark.

## 4. VM dispatch loop

The bytecode interpreter is the fast path of the language, so the loop that
runs it is worth a look. Three changes:

- The instruction pointer, the code array and the operand stack live in
  local variables. Reading `frame.ip` and `frame.stack` for every
  instruction was the single largest cost of the loop.
- The instruction is unpacked lazily: the opcode and the operand are read
  by index, and the line and the column are only read when an error is
  raised.
- The hot opcodes are handled inline, the cold ones go through the
  dispatch table.

**A scope per loop iteration, on purpose.** The body of a loop runs in its
own scope, so a closure that is created in the body captures the values of
that iteration and not the values of the last one:

```bun
var fns = []
for i in range(0, 3) {
    let x = i
    fns.push(fn() { return x })
}
print(fns[0]())   // 0, not 2
```

Hoisting the scope out of the loop would remove an `ENTER_SCOPE`, an
`EXIT_SCOPE` and an environment allocation per iteration — about 30% of the
instructions of a tight loop — but it would change the meaning of the
program. The scope stays.

## 5. Structured concurrency

```bun
scope {
    let a = spawn { return 21 * 2 }
    let b = spawn { return 7 }
    print(task_join(a))
    print(task_join(b))
}
```

### Runtime

`bun/tasks.py` owns the task registry and the task groups.

- A group is a list of the tasks that were spawned while the group was
  open. The group of the running thread is kept in thread-local state, so
  a task that spawns further tasks puts them into the same group.
- `scope_exit` joins every child of the group and returns the first error
  instead of raising it: the caller decides whether the error of the body
  or the error of a child wins.
- The error of the body wins. The body is the code that asked for the
  work, so its failure is the interesting one.

### Bytecode

```
SCOPE_ENTER          open a task group
TRY_FINALLY          the group is closed on the error path as well
<body>
END_TRY
SCOPE_EXIT           join every child, raise the first error
JUMP end
handler:
SCOPE_EXIT           join every child, keep the error of the body
FINALLY_END          raise the error of the body
end:
```

Leaving the scope early (a `return` or a `break` inside the body) closes
the group too: the unwinding code emits `SCOPE_EXIT` before the jump.

### Syntax

`scope` is a soft keyword. It only starts a scope statement when a block
follows it on the same line, so `let scope = 3` stays a valid program. A
hard keyword would have broken every program that uses the name.

`spawn { ... }` is sugar for `spawn(fn() { ... })`. The parser builds the
function literal and the call, so no new node type is needed.

### Cancellation

Cancellation is cooperative. `cancel(handle)` marks a task as cancelled
and `task_cancelled()` lets the task notice. A thread cannot be killed
safely: the task owns its own state and has to decide when to stop. The
group joins cancelled children like every other child.

### Parity

The self-hosted front end produces the same bytecode for the same program
(`tests/test_selfhost.py`), the self-hosted type checker produces the same
messages, and both engines produce the same output
(`tests/golden/scope.bun`).

## 6. The instruction profiler

The register VM is the big change that is still open, and it needs data:
which instructions are hot, and how often does each one run. Guessing is
not good enough for a change of that size, so the language can measure
itself.

```
$ bun compile --profile hot.bun
instruction profile: 26013 instructions
 15.39%       4003  LOAD_NAME
 15.38%       4000  ENTER_SCOPE
 15.38%       4000  BINARY
 15.38%       4000  EXIT_SCOPE
 ...
```

`bun compile <file.bun>` without the flag prints the bytecode of the file,
so the profile and the code can be read side by side.

The profiler counts the opcodes that the VM executed. The counts are a
proxy for the time, not the time itself: measuring the time per
instruction would cost more than the instruction. The distribution is what
matters for the register VM — a register VM pays for the *transfer* of a
value, so the opcodes that move a value the most are the ones that have to
disappear.

## 7. Measurements

Measured on the machine the work was done on — a shared 2.5 GHz Xeon vCPU.
The numbers are slow in absolute terms; the comparison between the engines
and against the old numbers is what matters.

| Measurement | Before | After |
|-------------|--------|-------|
| startup, tree engine | 165 ms | 55.3 ms |
| startup, VM engine | 165 ms | 55.2 ms |
| method benchmark, tree engine | 11.1 s | 7.3 s |
| method benchmark, VM engine | 6.9 s | 7.1 s |
| 50k iteration `while` loop, VM engine | — | 0.80 s |
| 50k iteration `while` loop, tree engine | — | 1.24 s |

The method benchmark calls `split` and `len` 300,000 times. The `while`
loop adds 1 to a counter 50,000 times. The startup numbers come from
`tools/bench.py` (the fastest of seven warm runs); the others are the
wall clock of the whole process, the startup included.

The method benchmark got a third faster in the tree engine, which spends
the larger share of its time in the method path. The VM engine is within
the noise of its old number: it already looked the method up once per
call, and the cache saves the walk through the `isinstance` chain, which
the VM did not do. The VM stays ahead of the tree engine on the loop
benchmark by a factor of 1.55.

The profiler costs about 3% of the run time when it is switched on. That
is the price of counting, and a profile is only taken when it is asked
for.
