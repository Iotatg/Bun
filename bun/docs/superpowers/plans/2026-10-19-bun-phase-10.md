## Objective

Close the gaps that a Python programmer trips over in the first hour with
Bun. The language is fast and it is small, but a few things that Python
has are missing, and their absence is felt in every program:

- there are no bit operators, so a mask, a flag or a hash is arithmetic
  with divisions;
- a `for` loop takes one name, so a table of pairs needs an index and a
  subscript on every turn;
- a dict cannot be walked, so `for key in data.keys()` is the only way;
- there is no `assert`, so a check is three lines of `if` and `throw`;
- there is no `match`, so a dispatch on the shape of a value is a chain of
  `if` statements that grows with every new case.

The five items are one phase because they are one kind of work: the
surface of the language, in the two pipelines, with the same error
messages.

## 1. The bit operators

Python's spelling, because the language is Python-like:

| Operator | Meaning |
|----------|---------|
| `a & b` | the bits that are in both |
| `a \| b` | the bits that are in one of them |
| `a ^ b` | the bits that are in one of them but not in both |
| `~a` | the bits of `a`, turned around |
| `a << n` | `a` moved `n` bits to the left |
| `a >> n` | `a` moved `n` bits to the right |

The operands are integers. A float or a string is a static error at the
checker and a runtime error in the interpreter, the same rule the
arithmetic operators follow.

**The precedence** is Python's, so the operators sit between the
comparison and the arithmetic:

```
or  <  and  <  not  <  == !=  <  < > <= >=  <  |  <  ^  <  &  <  << >>  <  + -  <  * / %  <  unary
```

The parser is a chain of one function per level, so the new levels are
four small functions in `bun/parser.py` and the same four in
`selfhost/parser.bun`.

**The shift of a negative number** moves the sign along, as in Python:
`-1 >> 1` is `-1`, not a huge positive number.

**The mask in the websocket** of `bun:web` is then one operator instead
of the eight-line loop that takes the bits out one by one.

## 2. `for a, b in ...`

A loop over pairs is the most common loop that is not over a list of
one thing:

```bun
for name, value in pairs {
    print(name + " is " + str(value))
}
```

The target of the loop is a list of names. The list that is walked must
have the same length as the names, and every element must be a list of
that length too. A shape that does not fit is a runtime error that says
what was expected and what came.

The rule is the same as the rule of the unpacking in an assignment, so
there is one shape rule in the language and not two.

## 3. `for key in a dict`

A dict is walked by its keys, as in Python:

```bun
for key in data {
    print(key + " = " + str(data[key]))
}
```

The keys come in the order they were put in, because the order of a dict
is part of its contract. A list, a string, a range and a dict are all
things that can be walked; anything else is a runtime error that names
the type.

`data.keys()` stays, and it means the same thing. The rule is one rule:
`for x in y` walks `y`.

## 4. `assert`

```bun
assert count > 0, "the count must be positive"
```

The message is optional. A failed assertion throws a runtime error whose
text starts with `assertion failed`. An assertion is a check of an
invariant, so it is a statement and not a function: it reads as a claim
about the program, not as a computation.

## 4b. The `else` of a loop

A loop may have an `else`: the block that runs when the loop ends without
a `break`.

```bun
for track in tracks {
    if track is broken {
        break
    }
    play(track)
} else {
    print("the queue is empty")
}
```

The `else` is the tail of the loop, so a `break` has to jump over it. The
compiler emits the loop, then the `else`, and the target of a `break` is
the end of the `else` instead of the end of the loop.

A loop has a scope of its own, so the name of the loop is gone when the
`else` runs. The checker knows this, and the name is an undefined
variable in the `else` — the same error the runtime gives.

## 5. `match`

The dispatch on the shape of a value:

```bun
match response {
    200 => print("ok"),
    404 => print("not there"),
    _ => print("something else"),
}
```

The patterns of the first version:

| Pattern | Matches |
|---------|---------|
| `200` | the value equals the pattern |
| `"text"` | the value equals the pattern |
| `x` | anything, and `x` is bound to the value |
| `_` | anything, and nothing is bound |
| `int` / `string` / `list` / `dict` | the type of the value |
| `1 to 9` | the value is in the range |
| `[a, b]` | a list of two items, and the items are bound |
| `[a, *rest]` | a list of two or more items, and the rest is bound |
| `{"id": id}` | a dict with the key, and the value is bound |
| `301, 302` | one of the patterns, the first one that matches |

The first matching case wins, and the cases are tried in the order they
are written. A `match` without a matching case and without a `_` case is
a runtime error that says what was matched against.

A case may name more than one pattern. The alternatives are tried in the
order they are written, and the names of the alternative that matches are
the names of the case:

```bun
match status {
    301, 302 => print("moved"),
    404 => print("not there"),
    _ => print("something else"),
}
```

The comma is the separator of the alternatives because it cannot be
mistaken for anything else: the alternatives come before the `=>`, and the
comma that separates two cases comes after the body of a case.

A case may also have a guard: a condition that has to hold for the case
to match. A guard that does not hold sends the case on to the next one,
the same way a pattern that does not match:

```bun
match size {
    n if n > 100 => print("big"),
    n if n > 10 => print("medium"),
    _ => print("small"),
}
```

The guard is compiled as code and not as part of the plan, because a plan
is data and a guard is an expression. The compiler emits the test of the
pattern, then the guard, and both have to hold for the body to run. The
guard is compiled in the scope of its own case, so it sees the names the
pattern binds.

A list pattern may have a tail: the rest of the list, bound to a name.

```bun
match [1, 2, 3] {
    [first, *rest] => print(str(first) + " and " + str(len(rest))),
    _ => print("no match"),
}
```

A list without a tail has to have the length of the pattern. A list with
a tail has to have at least the length of the fixed items, and the tail
takes the rest of the list. The `*` is the last item of the pattern, and
a `*` that is not the last item is a syntax error.

**Why this one is last.** It is the biggest of the five: the parser
needs a pattern grammar, the compiler needs to emit the tests, and the
checker needs to bind the names of a pattern. The other four items are
small and make the language usable; this one makes it interesting.

### How `match` is built

A pattern becomes a *plan*: a list that says what to test and what to
bind. The plan is the same in the two pipelines, so the tree engine and
the virtual machine test a value in the same way.

| Plan | Meaning |
|------|---------|
| `["literal", value]` | the value equals the literal |
| `["wildcard"]` | anything, and nothing is bound |
| `["binding", name]` | anything, and the name is bound to the value |
| `["type", name]` | the type of the value is the named type |
| `["range", low, high]` | the value is in the range |
| `["list", [plan, ...]]` | a list of that length, with the items bound |
| `["dict", [[key, plan], ...]]` | a dict with the keys, with the values bound |
| `["or", [plan, ...]]` | one of the patterns, the first one that matches |

The plan is the argument of one instruction, `MATCH_TEST`. The
instruction pops the value, tests it, and pushes the result. The names
are only bound when the whole pattern matches, so a pattern that fails
halfway does not leave half of its names behind.

The subject is evaluated once and kept in a hidden name, because a case
may be tried more than once and the subject may be an expression with a
cost. Every case has its own scope, so the names one case binds do not
leak into the next one.

`match` is a soft keyword, like `scope`: it only starts a match
statement when a subject and a block follow it, so `let match = 3` is
still a valid program. The parser looks at the tokens, and when they are
not a subject and a block, the name is used as an ordinary identifier.

The body of a case is one statement, or a block of statements. A dict
literal as the body of a case needs parentheses, because a `{` after `=>`
always starts a block.

Every item is tested on both engines, and the error messages of the
checker are compared between the two pipelines, the way
`tests/test_selfhost.py` compares them today.

The bit operators are tested against the values that Python gives for the

## 7. What is deferred

- **Class patterns** (`Point(x, y)`): they need a constructor call and a
  type that can be named.
- **Non-literal bounds of a range**: `low to high` takes two literals, so
  the plan of a pattern stays data. An expression bound would have to be
  compiled as code, the way a guard is.

## 8. What came after

- **The `not` operator as a word.** The language has the mark `!`, and
  the word form is Python's spelling. The word sits between `and` and the
  comparisons, so `not a == b` means `not (a == b)`. The parser lowers it
  to the mark, so the checker, the compiler and the runtime did not
  change: the two spellings are the same operation.
- **Keep-alive and chunked responses** in `bun:web`, with the Phase 9
  stack.
