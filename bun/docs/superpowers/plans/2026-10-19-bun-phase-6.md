# Bun Phase 6 — Pythonic Surface — Implementation Plan

Date: 2026-10-19
Design: `docs/superpowers/specs/2026-10-19-bun-advanced-language-design.md` §2
Research: `docs/superpowers/research/2026-10-19-bun-language-research.md` §2.4

---

## Objective

Close the gap between Bun and Python's surface language so that ordinary
Python-shaped code is directly expressible, without weakening the two things
that make Bun *Bun*: the two-channel error model (static errors are
uncatchable) and the `let`/`var` immutability discipline.

## Scope

| # | Feature | Files touched | Risk |
|---|---------|---------------|------|
| 1 | **f-strings** | lexer, parser, ast, checker, compiler, vm, interpreter, selfhost/{lexer,parser,checker,compiler} | Low |
| 2 | **Comprehensions** | parser, ast, checker, compiler, vm, interpreter, selfhost/{parser,checker,compiler} | Medium |
| 3 | **Default / variadic / keyword-only params + call-site kwargs** | ast, parser, checker, compiler, vm, interpreter, values, selfhost/{parser,checker,compiler} | High |

| 5 | **Slices** | lexer, parser, ast, checker, compiler, vm, interpreter, selfhost/* | Medium |

| 8 | **`Secret` type** | values, builtins, types, checker, selfhost/checker, ops, interpreter, vm | Low |
| 9 | **Undefined-name detection** | checker, selfhost/checker | Medium |

Ordered by (value / risk). Each item is independently shippable and
independently testable; the plan executes them in order.

## 1. f-strings

### Grammar

```
fstring_expr := "f" STRING
```

The lexer, on seeing `f"` or `f'` (and not `f` followed by an identifier
character), lexes the whole string body and emits a single `FSTRING` token
whose value is the raw body. The **parser** splits the body into parts.

### AST

```python
@dataclass
class FString:
    parts: list       # list of FStringPart
    line: int
    col: int

@dataclass
class FStringPart:
    literal: str | None   # set for literal text
    expr: Node | None     # set for an interpolated expression
    spec: str | None      # format spec, e.g. ".2f"
    conv: str | None      # "r" or "s"
```

The parser scans the raw body for `{`/`}`:

- `{{` → literal `{`; `}}` → literal `}`.
- `{` … `}` → an expression, parsed by recursively invoking the expression
  parser on the substring, then optional `!conv` and `:spec`.
- A trailing `=` inside the braces means "print the source text", which
  requires keeping the raw source of the expression.

To support `=` correctly, the parser must remember the source span. The
`Token` already carries line/col; the simplest correct approach is to keep
the raw substring and use the sub-lexer/parser on it, tracking offsets.

### Runtime

`FString` evaluates to a `str`. Each interpolated part is evaluated, then:

- `!s` → `str(value)`
- `!r` → a `repr`-like rendering (`bun/values.py` already has
  `quote_string()`)
- no conversion → `str(value)`, except floats use a compact rendering
- `:spec` → a Python-`format()`-compatible spec. Implement a small subset
  covering `{:<width}`, `{:>width}`, `{:^width}`, `{:0>width}`,
  `{:.{precision}f}`, `{:,}`, and the `d`/`f`/`s`/`x`/`o`/`b` type chars.

`Secret` values render as `"***"` in every conversion.

### Checker

The interpolated expressions are type-checked like any other expression.

### Self-hosted parity

`selfhost/lexer.bun` must emit an identical `FSTRING` token (same raw body).
`selfhost/parser.bun` must split it identically. The differential suite
compares ASTs, so any divergence is caught.

### Tests

- `tests/test_fstring.py` — parsing, all conversions, format specs,
  `{{`/`}}` escapes, `=` self-documenting form, nesting.
- `tests/golden/fstring.bun` + `.out`.

## 2. Comprehensions

### Grammar

```
list_comp := "[" [expr "for" ...] "]"
dict_comp := "{" [expr [":" expr] "for" ...] "}"
```

The distinguishing feature is that the comprehension body contains a `for`
clause, which is not valid in a plain list literal. The parser therefore
must backtrack: on seeing `[`, speculatively parse an element expression; if
the next token is `for`, it is a comprehension; otherwise it is a list
literal.

The current parser has no backtracking infrastructure, so **add one**: a
save/restore of the token index. `Parser` must expose `_save()` / `_restore()`
over the token list and the token cursor.

### AST

```python
@dataclass
class Comprehension:
    element: Node        # list comp: the value expression
    key: Node | None     # dict comp: the key expression
    value: Node | None   # dict comp: the value expression
    clauses: list        # list of ComprehensionClause
    is_dict: bool
    line: int
    col: int

@dataclass
class ComprehensionClause:
    target: Node         # the loop variable
    iterable: Node
    condition: Node | None
```

### Scope

The comprehension gets its own scope; the loop variable does not leak. This
matches Python and is important for the data-oriented style the research
recommends.

### Runtime

The tree-walker evaluates the comprehension directly. The VM gets a
dedicated `OP_COMPREHEND` that stores the clause list and a result list on
the frame, rather than desugaring to closures (which would allocate a
closure per iteration).

### Checker

- The loop target is a new mutable binding (`var`-like) inside the
  comprehension scope.
- The condition expression must be boolean-ish; the checker treats it the
  same way as an `if` condition.
- Reassignment of an outer variable inside a comprehension is an error
  (Python: "name is assigned to before global declaration" is a different
  thing; here we simply scope it).

### Tests

- `tests/test_comprehension.py` — list/dict forms, multiple `for` clauses,
  conditions, nested comprehensions, scoping, errors.
- `tests/golden/comprehension.bun` + `.out`.

## 3. Function parameters and call-site keyword arguments

### AST

```python
@dataclass
class Param:
    name: str
    type_name: str | None
    default: Node | None
    kind: str    # "positional" | "vararg" | "kwarg" | "posonly" | "kwonly"
```

`FnDecl.params` becomes a list of `Param` rather than a list of strings.

### Call semantics

- Positional arguments fill positional parameters in order.
- Keyword arguments fill parameters by name; a parameter may be filled
  positionally or by keyword, but not both.
- `*args` collects surplus positional arguments.
- `**kwargs` collects surplus keyword arguments.
- Defaults are evaluated at call time, in the function's scope, with
  earlier parameters already bound.
- A missing required argument is a `BunRuntimeError` naming the function
  and the parameter.
- An unexpected keyword is a `BunRuntimeError` naming the function.

### Checker

The checker needs parameter kinds to validate call sites:

- Too many positional arguments → error.
- Unknown keyword argument → error.
- A required parameter missing → error.
- A keyword argument to a `*args`-only function → error.
- Default expressions are type-checked in the parameter's scope.

### VM

`OP_CALL` must build the argument list by kind. The frame's local slots are
laid out as: positional params, then `*args` (a list), then `**kwargs` (a
dict), then keyword-only params, then locals.

### Self-hosted parity

`selfhost/checker.bun` needs the same call-site validation. The parity
suite's `CHECKER_ERROR_CASES` must be extended with the new error messages.

### Tests

- `tests/test_params.py` — defaults, varargs, kwargs, kwonly, posonly,
  call errors, default evaluation timing.
- `tests/golden/params.bun` + `.out`.

## 4. Unpacking

### Forms

```
let a, b = pair
let [x, y] = pair
let first, *rest = items
[a, b] = pair
```

### AST

```python
@dataclass
class Assign:
    targets: list   # each target is a Node or an UnpackTarget
    value: Node

@dataclass
class UnpackTarget:
    kind: str       # "tuple" | "list" | "star"
    targets: list   # nested
    name: str | None
```

### Runtime

Unpacking a non-iterable is a `BunRuntimeError` ("cannot unpack X").
The count must match exactly, except a single `*rest` absorbs the remainder
(possibly empty). `rest` is always a list.

### Tests

- `tests/test_unpack.py`.

## 5. Slices

### Lexer

`:` inside a subscript is currently a syntax error. The lexer needs a
`COLON` token (it may already have one for other uses — check).

### AST

```python
@dataclass
class Slice:
    start: Node | None
    stop: Node | None
    step: Node | None
    line: int
    col: int
```

### Semantics

Python semantics: negative indices from the end, out-of-range clamped,
negative step reverses. `xs[::2]`, `xs[1:4:2]`, `xs[::-1]`.

### Tests

- `tests/test_slice.py`.

## 6. `finally` and exception chaining

### AST

`TryStmt` gains a `finally_body: list[Stmt] | None`.

### Semantics

- `finally` runs on: normal completion, `return` from `try`, `break`/`continue`
  out of `try`, and an exception propagating out of `try`.
- If `finally` itself throws, that exception replaces the in-flight one.
- `throw value, cause` attaches a cause. The error object becomes a
  `BunError` with a `cause` field; `str(e)` renders `value` only, and the
  diagnostic renderer shows the cause chain.

### VM

The existing try-handler mechanism must be extended with a second handler
region for `finally`. `break`/`continue` already track try-handler depth
(`try_depth` in the compiler) — the `finally` region adds a third depth
counter so that a `break` inside `try` still runs the `finally` block
before jumping out.

This is the highest-risk item in Phase 6: the control-flow unwinding
interacts with the `scope_depth`/`try_depth`/`for_depth` machinery added
for `break`/`continue`. **Mitigation:** implement `finally` in the
tree-walker first, get the golden corpus green, then mirror in the VM,
then in the self-hosted compiler.

### Tests

- `tests/test_finally.py` — normal, return, break, continue, throw,
  nested, finally-throws.
- `tests/golden/finally.bun` — golden parity case.

### Status: done (2026-10-19)

Implementation notes that differ from the sketch above:

- The try statement gained an optional `catch` clause: `try { } finally { }`
  is valid on its own. `try { }` alone is still a parse error.
- `ThrowStmt` gained a `cause` field. `throw value, cause` raises a
  `BunRuntimeError` whose `cause` is the stringified cause. The catch
  parameter still binds the message string, so the cause is observed
  through the diagnostic renderer (`caused by: ...`) or the error object.
- The VM handler table now stores a kind per handler: `"catch"` (the
  original behaviour) and `"finally"`. A `finally` handler does not catch
  the error: it stores it in `frame.pending_error`, runs the finally
  region and `OP_FINALLY_END` re-raises it. An error raised inside the
  finally block therefore replaces the in-flight error.
- The compiler tracks a stack of try contexts (`_try_contexts`) instead of
  a depth counter. Each context records whether the statement has a catch
  clause, whether it has a finally block, the scope depth of the try body
  and the depth of the context in the stack.
- Leaving a try statement with `return`, `break` or `continue` inlines a
  copy of the finally block at the jump site. The copy runs after the try
  body scopes are left (so the finally block sees the same variables as on
  the normal path) and before the enclosing scopes are left.
- The finally region is entered by a jump on the normal path, by falling
  through from the catch clause, and by the VM handler when an error
  propagates. A single copy of the block serves all three paths.
- The self-hosted compiler mirrors all of the above; the AST and bytecode
  dumps stay byte-for-byte identical between the two pipelines.

## 7. `with`

### Syntax

```bun
with expr as name {
    body
}
```

Multiple items: `with a as x, b as y { ... }` — decide in Phase 6 whether to
support the comma form; the single-item form is the minimum.

### Protocol

The target value must be a dict with an `"__enter__"` key and an
`"__exit__"` key, each a callable. `__enter__` is called with no arguments
and its result is bound to the `as` name. `__exit__` is called with
`(error_or_null)` after the body, whether or not the body raised. If
`__exit__` returns `true`, the exception is suppressed.

### Errors

A `with` target that does not implement the protocol is a
`BunRuntimeError` naming the missing method.

### Tests

- `tests/test_with.py`.
- `tests/golden/with.bun` — golden parity case.

### Status: done (2026-10-19)

Implementation notes that differ from the sketch above:

- The comma form is supported: `with a as x, b as y { ... }` enters the
  managers left to right and exits them in reverse order.
- `as` is a soft keyword: it can still be used as a variable name.
- The target must be a dict whose `"__enter__"` and `"__exit__"` values are
  callables. `__enter__` is called with no arguments, `__exit__` with the
  error message (a string) or `null`.
- The managers that were entered are tracked in a per-frame stack
  (`frame.with_stack`). The exit sequence is a loop over that stack, so a
  manager whose `__enter__` failed is never exited, while the managers
  entered before it still are.
- The `__exit__` sequence is shared by the normal path and the error path.
  `OP_PENDING_ERROR` yields `null` when no error is in flight, so the same
  code serves both. The normal path pops the try handler *before* the exit
  sequence, so an error raised by `__exit__` propagates outwards instead of
  re-entering the same handler.
- A truthy `__exit__` result suppresses the error: the pending error is
  cleared (`OP_CLEAR_ERROR`) and `OP_HAS_ERROR` decides whether the error
  is re-raised with `OP_FINALLY_END`.
- `return`, `break` and `continue` inside a `with` body inline a copy of
  the exit sequence at the jump site, after the body scope is left.
- New ops: `OP_WITH_DEPTH`, `OP_HAS_ERROR`.

## 8. `Secret`

### Runtime value

`BunSecret` in `bun/values.py` wrapping a value.

### Builtin

```python
def _secret(args):
    _one("secret", args)
    return BunSecret(args[0])
```

### Redaction

- `str(secret)` → `"***"`.
- `canonical_dump` / `quote_string` → `"***"`.
- Any dict containing a secret dumps it as `"***"`.
- `dump()` of a structure containing a secret is redacted.

### Escape hatch

`secret.reveal()` → the wrapped value. This is the *only* way out, and it
is greppable.

### Types

`bun/types.py` and `selfhost/checker.bun` both need a `secret` entry:
`"secret": [((ANY,), "secret")]` — the checker gains a `secret` type name.

### Tests

- `tests/test_secret.py` — redaction in `str`, `dump`, dicts, lists,
  error messages; `reveal()` returns the value.
- `tests/golden/secret.bun` — golden parity case.

### Status: done (2026-10-19)

Implementation notes that differ from the sketch above:

- `BunSecret` lives in `bun/values.py`. It is an opaque wrapper: the
  runtime never inspects it, it only flows through values.
- The mask is the string `***` (`bun/values.SECRET_MASK`). It is used by
  `stringify`, `repr_value`, `format_value` and `canonical_dump`, so every
  rendering path is covered: `print`, `str`, `dump`, f-strings, dict and
  list contents, and error messages built from a thrown secret.
- `canonical_dump` renders a secret as the JSON string `"***"`, so a
  structure containing one stays valid JSON.
- The escape hatch is the `reveal` method, dispatched through
  `ops.method_call` like every other method, so `secret(x).reveal()` is
  the only way to get the value back. It is greppable on purpose.
- `type_of(secret(x))` returns `"secret"`. The checker learns the type
  name: `bun/types.py` and `selfhost/checker.bun` both carry a `secret`
  entry, so `var x: string = secret("a")` is a static error in both
  pipelines.
- Two secrets compare equal when their wrapped values compare equal; a
  secret never compares equal to its unwrapped value.

## 9. Cross-cutting work

### 9.1 `bun api --json`

Export the builtin signature table (`bun/types.py`) as JSON. This is the
machine-readable surface the design calls for (§7.2) and removes the need
for an assistant to read source.

```
$ bun api --json
{"builtins": {"print": [["any"], "null"], ...}}
```

### 9.2 `bun doc <symbol>`

A docstring registry. Builtins gain a `doc` field; `bun doc print` prints
it; `bun doc --json` emits it structured.

The docstrings live in a new `bun/docs.py` (Python) and
`selfhost/docs.bun` (Bun), keyed by symbol name, with the parity suite
checking that both agree.

### 9.3 `bun test --doc`

Runs every example in the docstring corpus and fails if one errors. This
makes the documentation self-verifying.

### Status: done (2026-10-19)

- `bun api [--json]` prints the builtin signature table. The JSON form is
  `{"builtins": {"print": [[["any"], "null"]], ...}}`; the plain form
  lists one signature per line. The table is the same one the checkers
  use, so the two can never drift apart.
- The docstring registry lives in `bun/docs.py` and is mirrored in
  `selfhost/docs.bun`. Every builtin has a `signature`, a `summary` and
  optionally `details` and a runnable `example`. The parity suite
  compares the two registries entry by entry.
- `bun doc <symbol>` prints one entry, `bun doc` lists the documented
  symbols and `bun doc --json` emits the whole registry.
- `bun test --doc` runs every example through the checker and the VM and
  fails when one of them errors. Examples never touch the network or the
  filesystem, so the command is hermetic.
- The self-hosted front end gained a `docs` mode (`selfhost/main.bun`)
  that dumps the registry, which is what the parity test compares.

## 9.4 Undefined-name detection

The checker resolves an unknown name to `any` and stays quiet. A program with
a typo in a name therefore runs until the name is used, and the error of the
runtime is far away from the mistake. The checker now reports the name.

### Rules

- A name is known when it is bound by a `let`, a `var`, a function, an
  import, a parameter, a loop variable, a catch parameter, a `with` item, a
  comprehension target or an unpacking pattern.
- The names of a module are collected before the statements are checked, so a
  function may use a variable of the module that is defined further down.
  The name of a function is known even when the function is defined further
  down.
- The names of a block are collected for the whole block, so the order of the
  statements is not part of the type. The check reports a name that is not
  bound anywhere, never a name that is bound later.
- The name of a builtin is always known.
- The name of a method and the name of a keyword argument are not variables.

### Message

```
undefined variable 'name'
```

The message is the same in the Python checker and in `selfhost/checker.bun`,
the parity suite compares it.

### Status: done (2026-10-19)

The check found three bugs in the bot on the day it was written: a missing
import of `set_current`, a call to a `delete` statement that the language
does not have, and a call to a `random` function that was never defined.

## 10. Execution Order

1. **f-strings** — lexer → parser → ast → runtime → checker → selfhost.
2. **Slices** — small, independent, needed by comprehensions' ergonomics.
3. **Comprehensions** — needs parser backtracking.
4. **Function parameters** — the largest change; touches the call path in
   both engines.
5. **Unpacking** — depends on the new `Assign` shape.
6. **`finally` + chaining** — the highest control-flow risk.
7. **`with`** — depends on `finally` machinery.
8. **`Secret`** — independent; can be done at any point.
9. **Undefined-name detection** — independent; the checker only.
10. **Cross-cutting** — `bun api --json`, `bun doc`, `bun test --doc`.

After each item: run the full suite (`python3 -m pytest tests/ -q`), then
the self-host suite (`python3 -m pytest tests/test_selfhost.py -q`, ~170 s),
then the golden corpus.

## 11. Builtins added while building the bot

The bot needed a few primitives that the language did not have yet. Each one
is small, is covered by a test, and is documented in the registry so that
`bun doc` and `bun test --doc` know about it.

| Builtin | Signature | Why the bot needed it |
|---------|-----------|----------------------|
| `input` | `input(prompt?)` | the login flow reads the phone number and the code from the terminal |
| `random` | `random()` | the shuffle of a playlist needs a number between zero and one |
| `random_int` | `random_int(low, high)` | the same, with a whole number |
| `exec` | `exec(command, timeout?)` | the downloader falls back to `yt-dlp` when the format is ciphered |
| `http_get_bytes` | `http_get_bytes(url, headers, timeout)` | the InnerTube client needs the bytes of a response |
| `write_bytes` / `read_bytes` | `(path, data)` / `(path)` | the session store keeps the auth key in a file |
| `utf8_bytes` / `utf8_string` | `(text)` / `(data)` | the TL layer needs UTF-8 as bytes |
| `bigint_*` | see `bun doc bigint_add` | the RSA layer needs exact modular arithmetic |
| `aes_ige_encrypt` / `aes_ige_decrypt` | `(data, key, iv)` | the MTProto envelope |
| `h2_connect` / `h2_request` / `h2_close` | see `bun doc h2_request` | HTTP/2 with HPACK for the general case |

The optional second argument of `exec` is the timeout in seconds. A timeout
that expires raises `exec() timed out: <argv0>`; a negative timeout raises
`exec() expects a non-negative timeout`.

The documentation examples of the network and the filesystem builtins are
hermetic: they use a byte list or a fixed input instead of the real
service, so `bun test --doc` never touches the network.

## 12. Definition of Done

- Every feature in scope has unit tests and a golden case.
- The tree-walker and the VM agree on every golden case.
- The self-hosted front end produces **byte-identical** error messages for
  every new construct (extended `CHECKER_ERROR_CASES` in
  `tests/test_selfhost.py`).
- `bun check --json` emits structured diagnostics for every new error.
- The golden corpus passes under all four engine combinations.
- `docs/reference/compatibility.md` records every difference from Python
  introduced by Phase 6.

### Status: done (2026-10-19)

- The features of Phase 6 are in the language, in both pipelines, with the
  tests of the plan.
- `bun check [--json] <file>` type checks a file or a directory without
  running it. The JSON form is
  `{"ok": bool, "diagnostics": [{"file", "severity", "kind", "message",
  "line", "col"}]}`, where `kind` is `type`, `syntax` or `lex`.
- `docs/reference/compatibility.md` records the differences between Bun and
  Python, and `tests/test_bot_commands.py` runs the commands of the music
  bot against a stub of the Telegram client.
